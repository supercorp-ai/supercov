## Real apps, configuration, and exclusions

### Bulletproof React

Pinned to [9506629](https://github.com/alan2207/bulletproof-react/tree/9506629ed003a561c6627735480cce4994244bb4),
`apps/react-vite`, using its Yarn lockfile, Vite/Vitest configuration, documented
`.env.example`, React 18, Testing Library, MSW, React Query, React Hook Form,
Zod, Radix and path aliases. Tests include authentication forms, permissions,
discussion CRUD and comments. No application tests or assertions were rewritten.

The automatic source inventory flags four files outside `src`: component
scaffolding, the mock server, Plop configuration, and MSW's generated worker.
The verified CI run uses `SUPERCOV_SOURCE_ROOTS=src` to explicitly select the
application. All 21 tests pass, with zero measurement limitations. Automatic
inventory warnings were not silently suppressed in the product.

### Bluesky

Pinned to [a75324b](https://github.com/bluesky-social/social-app/tree/a75324b378f13a1a2fb31cd47af7f0f1b4c606bb).
The run retains the pnpm lockfile and patches, Expo 57, React Native 0.86,
`jest-expo/ios`, the native mock setup, module aliases, Lingui transforms and
React Compiler Babel configuration. Its existing suite exercises application
logic, hooks/state, storage, networking mocks and snapshots. It is not a test of
every rendered screen or a device build.

One file, `__tests__/lib/string.test.ts`, cannot run in this checkout without a
generated English translation catalogue. Both baseline and instrumented runs
exclude that same file. The baseline without the exclusion fails before that
file's tests execute; the remaining 74 suites pass.

Both runs disable pnpm's `verifyDepsBeforeRun` using
`pnpm_config_verify_deps_before_run=false` **after a frozen-lockfile install**.
The isolated workspace shares the installed dependencies; pnpm 11 otherwise
attempts an automatic reinstall because workspace metadata differs. This is a
recorded compatibility setting, not a claim that arbitrary pnpm 11 invocations
are now zero-configuration. See the [pnpm setting](https://pnpm.io/settings#verifydepsbeforerun).

The original adapter merged duplicate Jest titles and misclassified one
execution as an unknown retry. The corrected adapter agrees with Jest exactly:
837 total, 809 passing, 28 skipped, zero failures and zero unknown outcomes.
Parameterized duplicate names and delayed retries now have dedicated regression
coverage.

## Changes

- Configure resolved Vitest projects individually, and register browser evidence
  commands when each browser instance is initialized. Keep user setup and
  commands. Cover config files/globs, inline extends, root inheritance and
  selection with real Chromium.
- Preserve browser module-initialization coverage separately from test evidence.
- Bridge Babel-generated CommonJS runtime imports into Jest's existing runtime,
  including jsdom before user setup imports application code.
- Preserve the original Jest config through Expo's forwarding launcher; prevent
  recursive loading and heap exhaustion.
- Exclude manifest-declared Jest setup files from application instrumentation,
  preventing injected bindings from breaking Babel's hoisted mock factories.
- Distinguish duplicate Jest test declarations from retries. Final outcomes use
  Jest's declaration-ordered result array, while runtime evidence uses Circus's
  corresponding declaration tree.
- Capture per-test evidence after Testing Library/user teardown so effect cleanup
  is retained and attributed to its test.
- Synchronize and check the embedded runtime assets.

## Boundaries

React Native support demonstrated here is JavaScript testing through Jest and
its native mocks. There is no validation here of Hermes execution, Metro on a
device, Swift/Objective-C/C++ modules, simulators, device E2E, Detox or Maestro.
Those need native execution and evidence-transport integrations.

The hydration fixture does not establish Next.js Server Components, streaming
SSR or server actions. Do not turn the fixture into a blanket Next.js claim.

The four UI maps are reviewed explanations backed by observed passing assertions
and matching statement execution. They are neither automatic semantic inference
nor mutation-resistance guarantees. The demo independently edits four copies to
check four specific regressions.

No speed or token-savings claim was measured. In one local debug-binary nightly
run, Bluesky took about 79 seconds end to end; its baseline Jest run was much
shorter. Instrumentation and evidence processing are material costs at this
application size, which is why the full application check belongs in nightly CI.
